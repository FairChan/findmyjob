## 1. 系统概要

- **形态**：Next.js 全栈单体（app + worker）+ PostgreSQL 16 + Caddy，Docker Compose 跑在马来西亚区域的一台主机上；文件放 S3 兼容的私有桶（ARCHITECTURE §1–§3、§7）。GATE-M7 之前这台主机就是 staging，只放合成数据（A22）。
- **用户**：学生（免费建档、投递，查看职位详情有额度）、企业成员（企业通过认证后搜人才库、花点数解锁联系方式）、平台运营（后台）。
- **关键数字**（PRD §5 默认值，运营可在后台改）：
  - 学生注册上限 3000，按 E2 200 人 → E3 500 人 → E4 3000 人放量（A28）。
  - 学生登录后可看 20 个职位详情；每 3 个有效邀请多 10 个；累计 12 个后不限。
  - 公益期每家认证企业每月补足到 30 点，解锁一次 1 点；每家企业每天最多看 400 份详情，每个成员 200 份；团队最多 3 人。
- **关键数据流**：
  1. 企业搜人才库 → 匿名卡片（`talent-card` 序列化、自由文本 redact）→ 详情页（记 ProfileView）→ 解锁（一个事务里：TalentUnlock → 扣点 → 记账 → 审计）→ 经 `contact-access` 解密联系方式；简历经服务端重建、加水印后下载（ARCHITECTURE §5.2、§5.3、§5.5）。
  2. 学生投递 → 同一事务里建 `TalentUnlock(source=APPLICATION)`，企业不扣点就能看联系方式（A3）。企业邀请投递、学生接受，也算投递。
  3. 学生打开职位详情 → `job-view-quota` 计数；邀请的同学达标后加额度（ARCHITECTURE §5.9）。
  4. 上传经 app 中转进私有桶；下载用 ≤ 300 秒的签名 GET，或由服务端流式返回（D17）。
  5. 运营后台：企业认证审核、职位审核、代管企业、调点数、加额度、系统参数、审计查询、数据请求（PRD §4）。

## 2. 资产

| 资产 | 存在哪里 | 为什么敏感 |
|---|---|---|
| 学生联系方式（手机、联系邮箱、WhatsApp、微信、LinkedIn） | `StudentContact`，AES-256-GCM 加密（ARCHITECTURE §5.2） | 平台收费的核心；落到诈骗方手里，学生会被直接联系；PDPA 下的个人数据 |
| 学生全名、原始简历 PDF | `StudentProfile.fullName`；`ResumeFile` + 对象存储 `resumes/` | 解锁前不该给企业；简历里通常还有照片、地址和联系方式 |
| 档案其他字段（学校、专业、毕业年月、CGPA、国籍、工作资格、期望薪资、经历） | `StudentProfile`、`Education`、`Experience`、`StudentLanguage` | 组合起来能认出人（TM-004）；工作资格反映签证身份，留学生容易因此被施压或被骗 |
| 学校邮箱 | `StudentProfile.schoolEmail`（明文、唯一） | 能直接联系到学生，也是学校认证的凭证 |
| 求职行为记录 | `ProfileView`、`TalentUnlock`、`Application`、`Invitation`、`JobView` | 透露「谁在找工作、被谁看过」 |
| 企业认证材料 | 对象存储 `verifications/`、`CompanyVerification` | 可能含董事或经办人的个人信息；也是攻击运营的载体（TM-016） |
| 「已认证企业」这个身份 | `Company.verificationStatus` | 有了它就能进人才库、发职位，是诈骗方最想要的东西 |
| 点数 | `CreditWallet`、`CreditLedger` | 决定能解锁多少人；M8 之后就是钱 |
| 账号和会话 | `User`、`Account`（密码哈希）、`Session`、`Verification` | 拿到就能冒充对应角色 |
| 运营账号 | `User.role = ADMIN` | 能看全部数据、改全部参数 |
| 审计和同意记录 | `AuditLog`（含 IP）、`Consent`（含 IP、UA） | 事故调查和合规证据；本身也是个人数据 |
| 导出包和备份 | 对象存储 `exports/`（明文 zip）、备份桶（age 加密） | 一份完整的个人数据副本 |
| 锁定职位的正文 | `Job.description`、`requirements`、`benefits`、隐藏的薪资 | 学生额度机制靠它；不是 PII |
| 注册名额 | `signup.studentCap` | 控制放量节奏，和压测结果挂钩 |
| 密钥（PII_KEYS、BETTER_AUTH_SECRET、S3 凭据） | 主机 `/opt/findmyjob/env/`、两人的密码管理器 | 存放和轮换由 ARCHITECTURE §7、A19 处理，本文件不展开 |

## 3. 参与者与攻击者

| 参与者 | 正常能做什么 | 作为攻击者想要什么 |
|---|---|---|
| 访客（公网任何人、爬虫、聊天软件的链接预览） | 职位列表、企业主页、反诈页 | 拿锁住的职位内容；批量注册；用平台发邮件骚扰别人 |
| 学生 | 自己的档案、投递、额度、邀请 | 刷额度；占名额；在档案里藏联系方式 |
| 企业成员（RECRUITER / ADMIN / OWNER） | 本企业的人才库搜索、解锁、职位、投递管理 | 不花点数拿联系方式；看别家企业的数据；团队内抢权 |
| 不良企业、中介、诈骗团伙 | 通过认证后同上 | 批量收集学生资料；用假职位或邀请附言行骗 |
| 盗号者 | 取决于盗到的账号 | 用企业号拿 PII；用运营号拿全部 |
| 平台运营（ADMIN） | 后台全部功能 | 内部滥用（少见，但影响大） |
| 子处理者（邮件、错误监控、人机验证） | 收到规格允许的数据 | 不当作主动攻击者，只看跨境和披露（TM-033） |

不在范围内：开发期 AI 中转和本机（阶段 0）；云厂商内部人员；国家级攻击者；主机、SSH 和网络层（由 M7-H01 和 GATE-M7 的检查项覆盖）。

## 6. 等级怎么定

- **High**：后果是学生 PII 被不该看的人拿到、学生被骗、或运营后台被接管，而且现在的规格里没有确定性的控制（测试、数据库约束、必填字段）挡住。每个 High 都要有去处（§11）。
- **Medium**：后果较轻，或已有部分控制，剩下的缺口可以靠人工发现、事后补救。
- **Low**：规格和测试基本已经覆盖；列出来是为了在评审时确认覆盖范围。
- **可能性**：高 = 不需要特殊技能，动机常见，或者正常使用就会发生；中 = 需要一定投入或特定条件；低 = 需要较强能力或少见的动机。
- **待核实**：写本文件时没法确认，要在实现或评审时查证。

## 7. 威胁清单

### TB1 企业与学生数据边界

#### TM-001 越权读取，以及序列化出口之外的泄漏

- **边界**：TB1
- **场景**：
  1. 企业成员把详情页、简历下载、收藏夹接口里的 studentId / resumeId / folderId 换成别的值，或者在请求里带上别家企业的 companyId。
  2. 页面把整条 Prisma 记录传给客户端组件，全名和联系方式随 RSC 载荷一起下发；或者响应被缓存后发给了别人。
  3. 企业侧通知、每日汇总邮件、日志、Sentry 事件里带出学生全名或联系方式。
- **影响**：未解锁就拿到学生身份；跨企业看到别家的收藏、备注、投递。
- **可能性**：中（页面由 AI 按任务逐个写，新页面最容易漏）
- **等级**：Low
- **现有控制**：ARCHITECTURE §5.1（companyId 只来自 `requireCompanyMember()`，`require*` 每次查库）、§5.2（talent-card 唯一出口、防泄漏单元测试）、§5.8（no-store，不用 `'use cache'`）、§5.13（pino redact、scrubEvent）；M1-T03（authz-matrix）；M4-T02、M4-T13（扫全部 HTML、RSC、JSON 响应）；M5-T03（职位侧用例）；M7-T05（每个企业侧 service 都有「其他企业被拒」用例）；M0-T08、M7-T04；GATE-M4 人工逐项。
- **缺口**：pii-leak.spec 只覆盖人才搜索页、详情页和职位页；后加的收藏夹（M4-T11）、邀请（M5-T07）、通知中心（M5-T08）没有要求加进去。架构测试 M1-T07 是 P1。
- **建议去处**：M4-T11、M5-T07、M5-T08 各加一句「本任务的企业侧页面加进 pii-leak.spec」；GATE-M7 复核。

#### TM-002 用关键词搜索试探被隐藏的联系方式

- **边界**：TB1
- **场景**：
  1. 学生在一句话介绍里写「加微信 leakwx0420」，或者把手机号写进技能标签、经历标题。企业侧显示时这些都被替换成「[已隐藏]」。
  2. 未解锁的企业先用学校、专业、毕业年份筛选，把结果缩到这一个学生。
  3. 再用关键词逐位试探：搜「微信 l」「微信 le」……或者「012」「0120」……看这个学生还在不在结果里。人才库关键词是对原文做 ILIKE（ARCHITECTURE §5.4「人才库搜索」），所以能一位一位拼出完整号码。一个 11 位手机号大约 100 次搜索，在每天 300 页的上限之内。
- **影响**：不花点数、不留解锁记录就拿到联系方式，绕过付费解锁和「谁解锁了我」；学生不知道。
- **可能性**：中（需要有心人，但手法简单；把微信号写进简介在学生里很常见）
- **等级**：High
- **现有控制**：显示时 redact（ARCHITECTURE §5.2、M4-T01、M4-T02）；`limits.searchPagesPerDay` 限制试探速度（M4-T03）。职位搜索已经有同类规则「搜索不能泄露看不到的内容」（ARCHITECTURE §5.4、M5-T09），来自原型 commit 审查发现的同类问题。
- **缺口**：
  - 同类规则没有扩展到人才库搜索。
  - redact 的覆盖清单里没有 `StudentProfile.major` 和 `Education.schoolName`（学校不在列表里时手填），卡片上却直接显示专业和学校；学生把联系方式写在这两处会原样显示。（待核实：卡片的「学校」取 School 还是 schoolName）
  - 只匹配脱敏文本，要么另存一份脱敏副本并把 trigram 索引建在副本上（改 schema），要么让这些字段不参与关键词匹配（搜索效果变差）。要在 M4-T03 之前定（A-13）。
- **建议去处**：TASKS M4-T03 加验收句；M4-T02 补一句专业和学校名也过 redact（§11）。

#### TM-003 「已解锁」在不同页面判断不一致

- **边界**：TB1
- **场景**：
  1. 企业 A 解锁了学生 B，或者 B 投递过 A 的职位。
  2. B 屏蔽了 A、被运营停用，或申请删号（软删除后的 30 天内数据还在）。
  3. `getContactForCompany` 会拒绝（ARCHITECTURE §5.2 写了三项检查），但收藏夹、邀请列表、投递看板各自计算 `unlocked`，只看 TalentUnlock 在不在，于是继续显示全名；简历下载（M4-T09）只查「TalentUnlock 存在且未被屏蔽」，没查删号和停用，删号期内照样能下。
- **影响**：违反 PRD §2.3「即使之前已解锁，也不再显示联系方式」；删号期内简历仍能下载，是 PDPA 问题。
- **可能性**：高（判断散在 5 个以上的任务里，由 AI 分别实现）
- **等级**：High
- **现有控制**：ARCHITECTURE §5.2 的三项检查；M4-T08 集成测试（屏蔽、删号后拒绝）；M4-T09 下载前校验；M4-T11 加收藏前调 `isStudentVisibleToCompany`；GATE-M4「学生屏蔽企业后…即使之前已解锁，也看不到联系方式」。
- **缺口**：`toTalentCard` / `toTalentDetail` 的 `unlocked` 由调用方传入，规格没说怎么算，也没有统一的函数；停用学生对已解锁企业是否可见没写（A-10）；学生投递后又屏蔽该企业怎么处理没写（A-11）；收藏夹只在加入时检查可见性。
- **建议去处**：TASKS M4-T08 加验收句（主），M4-T09、M4-T11、M5-T05、M5-T07 各加一句（§11）。

#### TM-004 从匿名卡片认出学生

- **边界**：TB1
- **场景**：试点只有一所学校、几百名学生。HR 在未解锁详情页看到学校、专业、毕业年月、语言、技能，以及经历的标题和机构名（机构名只去掉联系方式，单位名照常显示）。拿这些去领英、小红书或同校熟人那里一对，就能认出人，再私下联系。
- **影响**：学生以为是「匿名档案」，实际可以被认出；企业不付点数就能接触学生，学生也收不到「被解锁」通知。
- **可能性**：高（几乎不需要技术）
- **等级**：Medium（试点期点数免费，商业损失小；主要问题是对学生的告知不准确）
- **现有控制**：mask-name（M4-T02）；redact（M4-T01）；人才库默认不加入、需要主动勾选（PRD §2.1）；查看上限（M4-T05）。
- **缺口**：同意文案写的是「匿名档案」，没提示可能被认出；机构名在解锁前就显示。
- **建议去处**：A-14 二选一：(a) 接受，把注册勾选项和隐私中心的文案改成「企业可能凭学校、专业和经历认出你」（M1-T02、M2-T07），并写进 DECISIONS 已接受风险（§10）；(b) 解锁前不显示机构名（M4-T02）。

#### TM-005 认证企业批量爬取人才库

- **边界**：TB1
- **场景**：一家通过认证的企业（或者借壳的中介）用 3 个成员账号，每天合计看 400 份详情、每人翻 300 页搜索，一周内把 500 人的人才库全部存下来，转卖或给别的平台用；也可以反复用 1–2 个字的关键词让数据库做全表扫描。
- **影响**：匿名档案被批量带出平台（再加上 TM-004 就能对上人）；数据库变慢。
- **可能性**：中
- **等级**：Medium
- **现有控制**：PRD §3.2 防爬（成员级和企业级上限、同一学生当天只计 1 次、翻页上限、没有批量导出）；M4-T03、M4-T05；`limits.unlocksPerDay`；公益期每月只有 30 点；触发上限写审计 `talent.limit.hit`；DECISIONS 已接受风险第 5 行（短关键词全表扫描）。
- **缺口**：翻页数没有对应的业务表，P1（M7-T14）之前只能在内存里计数，重启或发版就清零（待核实：M4-T03 怎么计）；触发上限只写审计不告警，E8-02 不采用，靠运营巡查。
- **建议去处**：M7-T13 的每周例行检查加一项「本周 `talent.limit.hit` 最多的 5 家企业」；E4 前按 E8-02 复评。

### TB2 企业认证和团队

#### TM-006 虚假或冒用的企业通过认证

- **边界**：TB2
- **场景**：
  1. 诈骗团伙或中介用私人邮箱注册企业账号，填一家真实公司的法定名称和 SSM 注册号。
  2. 认证材料上传这家公司的 SSM 资料（这类资料一般能付费查询到，具体渠道待核实）或改过的执照。
  3. 运营看材料「对得上」就点了通过，没有按 SOP 回拨。企业立刻拿到人才库搜索、每天 400 份详情、每月 30 点解锁和发职位的资格。
  4. 变体：抢先用别家公司的 SSM 号注册，真公司来注册时因为 SSM 号唯一被挡住。
- **影响**：学生联系方式落到诈骗方手里；用真实公司名义发假职位，学生被骗（A27 认为招聘诈骗是留学生最大的风险之一）；平台信誉受损。
- **可能性**：中
- **等级**：High
- **现有控制**：PRD §3.1、§4 的认证 SOP（通过公开渠道回拨核实，不用材料里自带的联系方式）；M3-T02（documentKeys 只能是本企业的上传）；M3-T03（审核页提示 SOP、驳回必须填原因、审计 `company.verify`）；A27 职位全部人工审核；D18 的各项上限。
- **缺口**：SOP 只是审核页上的提示，系统不要求留下核实记录，事后查不出有没有回拨过；企业邮箱域名不做任何校验（A-3）；通过认证后没有观察期。
- **建议去处**：TASKS M3-T03 加验收句（§11）。

#### TM-007 职位被用来诈骗或收集学生资料

- **边界**：TB2
- **场景**：
  1. 认证企业发一个正常职位，运营审核通过（A27）。
  2. 之后企业编辑这个职位，把描述改成「入职先交培训费」「加 WhatsApp 详聊」「高薪赴外地」。规格没说编辑已发布的职位要重新审核（M5-T01 只写了「编辑」），新内容直接给学生看。
  3. 变体：发一个看起来正常、其实不招人的诱饵职位，学生一投递，企业就免费拿到联系方式和简历（A3），用来转卖或诈骗。
  4. 试点期学生在站内可能没法举报：职位举报（M7-T09）和举报队列（M6-T08）都是 P1。
- **影响**：学生的财产损失，甚至人身风险；平台信誉。
- **可能性**：中
- **等级**：High
- **现有控制**：A27、M5-T01、M5-T02（首次发布人工审核，审计 `job.review`）；TM-006 的认证；反诈专区和举报（M7-T09，P1）。
- **缺口**：编辑后不重新审核；举报在试点期可以不做（和 PRD §2.6 不一致，见 §9）；诱饵职位单靠审核很难识别。
- **建议去处**：TASKS M5-T01 加验收句（§11）；举报是否提前见 A-6。

#### TM-008 代管企业被移交给冒充者

- **边界**：TB2
- **场景**：
  1. 运营为某公司代建账号并直接认证，代发了几个职位（代发不经审核，M6-T07）。
  2. 有人自称该公司 HR，发消息说「请移交到某个私人邮箱」。
  3. 运营调用 `transferCompany`，系统按团队邀请机制把链接发到这个邮箱；对方接受后成为 OWNER，平台账号退出。
  4. 对方现在拥有一个「已认证、品牌真实、有在招职位」的企业账号，可以改职位（TM-007）、搜人才库、解锁。
- **影响**：同 TM-006，而且更难察觉：品牌是真的，认证是平台自己做的。
- **可能性**：中（运营急着让企业接手时最容易发生）
- **等级**：High
- **现有控制**：M6-T07（复用 M3-T04 的邀请：绑定邮箱、一次性、7 天过期；移交后平台账号失去权限）；审计 `company.managed.transfer`；PRD §4「每一步都写审计」。
- **缺口**：没有规定怎么确认目标邮箱真的属于这家公司；回拨 SOP 只写在认证审核里，没写在移交里。
- **建议去处**：TASKS M6-T07 加验收句（§11）。

#### TM-009 代管期间平台账号的企业身份不清

- **边界**：TB2
- **场景**：同一个平台账号是多家代管企业的 CompanyMember。`requireCompanyMember()` 只返回一个 companyId，实现时很可能改成「从请求参数里取当前企业」，正是 ARCHITECTURE §5.1 禁止的写法；校验一写错，就能以任意企业身份操作。另外，代管企业已认证、有钱包和公益点数，这个账号可以以企业身份搜人才库、解锁，而 PRD §1 的权限矩阵规定平台 ADMIN 不能解锁。
- **影响**：越权；运营绕过「不能解锁」拿到联系方式。
- **可能性**：中
- **等级**：Medium
- **现有控制**：M6-T07（每一步写审计，移交时删除平台账号的成员记录）；ARCHITECTURE §5.1；PRD §4。
- **缺口**：M3-T01 的验收「一个企业用户只能属于一家企业」和代管做法矛盾（§9）；平台账号能否以代管企业身份用人才库没写（A-7）。
- **建议去处**：先回答 A-7，再在 M6-T07 加一句「代管企业不能搜人才库、不能解锁（或者允许，但每次写审计）」，并写明平台账号怎么确定当前企业（例如每家代管企业一个独立账号）。

#### TM-010 团队内越权

- **边界**：TB2
- **场景**：
  1. 企业 ADMIN 发一个 role=OWNER 的邀请给自己的小号，或者把自己改成 OWNER（`CompanyInvite.role` 可以取 OWNER，规格只写了「OWNER 不可被移除或降级」）。
  2. ADMIN 把其他 ADMIN 移除，独占企业。
  3. 一个学生账号用被邀请的邮箱接受团队邀请，同时成了学生和企业成员。
- **影响**：企业内部抢权；学生账号进入企业侧，越过角色边界。
- **可能性**：低到中
- **等级**：Medium
- **现有控制**：M3-T04（令牌只存 sha256、绑定已验证邮箱、只能用一次、7 天过期、`team.maxMembers`、被移除成员下一次操作就失效、OWNER 不能被移除或降级、RECRUITER 不能管团队、加进 authz-matrix）；GATE-M4（换账号打开邀请链接被拒，同一链接第二次使用被拒）。
- **缺口**：谁能授予哪个角色没写；接受邀请的账号必须是 EMPLOYER、且不属于别家企业，没写进验收。
- **建议去处**：M3-T04 加验收句「邀请和改角色都不能产生第二个 OWNER；STUDENT 账号、已属于别家企业的账号接受邀请被拒」（按 A-9 的答案定）。

#### TM-011 企业账号被盗

- **边界**：TB2
- **场景**：HR 在别处泄露的密码被拿来撞库；或者钓鱼邮件仿冒 FindMYJob 骗 HR 登录。盗号者登录后搜人才库、解锁、下载已解锁学生的简历。
- **影响**：每个被盗账号每天最多 200 份详情、50 次解锁（受企业点数限制），以及该企业已解锁的全部联系方式和简历。
- **可能性**：中
- **等级**：Medium
- **现有控制**：ARCHITECTURE §5.8、§5.11（登录 60 秒 5 次、Turnstile、改密码撤销其他会话、重置后撤销全部会话、防枚举）；M1-T01、M1-T05；审计 `auth.login`；简历水印带操作人 ID（M4-T09）。
- **缺口**：企业账号没有 2FA（M6-T09 只给运营）；没有新设备登录提醒；限流按 IP，分布式撞库主要靠 Turnstile 挡。
- **建议去处**：E3 前复评是否给企业 OWNER / ADMIN 开可选 2FA（M6-T09 已经引入 twoFactor 插件）。

### TB3 点数账本

#### TM-012 账本被并发、错误参数或任务重跑打乱

- **边界**：TB3
- **场景**：
  1. 余额 1 点时同时点两次解锁，或者同时解锁 10 个学生。
  2. 运营把 `unlock.costCredits` 误设为 0 或负数（负数会让每次解锁反而加点），或者把 `pilot.monthlyCredits` 设得很大。
  3. `pilot-monthly-credits` 在同一个月被重跑，或者 worker 在补点途中崩溃。
  4. 有人想直接改 CreditLedger 来掩盖。
- **影响**：点数凭空增加或扣错。公益期点数没有现金价值，主要后果是解锁次数失控，间接放大 TM-005。
- **可能性**：低
- **等级**：Low
- **现有控制**：ARCHITECTURE §5.3（唯一约束 + 带条件的 updateMany + 同一事务记账）；M4-T06、M4-T07（并发测试）；M4-T10（补足制、同月重跑不多发、每日对账告警）；M0-T03（`findmyjob_app` 不能改、删账本）；`credits.adjust` 必须填原因并写审计；GATE-M4 人工连点测试。
- **缺口**：M6-T05 只写了「按类型校验」，没有取值范围；REFUND 有枚举值但没有退款流程（试点期用不到）。
- **建议去处**：M6-T05 加一句「数值参数有最小值和最大值，`unlock.costCredits` 小于 1 时拒绝」；GATE-M8 前复评（A-1）。

#### TM-013 （M8）伪造转账回单或伪造支付回调

- **边界**：TB3
- **场景**：企业上传改过的银行转账回单，运营只看回单就确认到账；或者重放、伪造支付回调。
- **影响**：白拿点数或套餐。
- **可能性**：中（M8 开始收费之后）
- **等级**：Low（试点期不存在；M8 有专门的任务和闸门）
- **现有控制**：M8-T02（重复确认不重复发点、只有 OWNER 能下单、审计 `order.confirm`）；M8-T03（验签、按 externalRef 幂等）；GATE-M8（每月订单和账本对银行流水、Stripe 测试模式 differential-review）。
- **缺口**：「只以银行流水为准，不看回单」没写成 SOP；PAYMENT_PROOF 的对象 key 规则没写（ARCHITECTURE §5.5）。
- **建议去处**：GATE-M8 前复评；M8-T02 加一句 SOP。

### TB4 上传下载

#### TM-014 伪装文件上传

- **边界**：TB4
- **场景**：把 .exe、HTML、SVG 改名成 .pdf 或 .png 上传；传超大文件、30 页 PDF、加密 PDF；绕过页面直接 POST。
- **影响**：存储型 XSS、把恶意文件传给企业或运营、撑爆存储。
- **可能性**：中
- **等级**：Low
- **现有控制**：ARCHITECTURE §5.5（app 中转、按用途白名单、文件头、SVG/HTML/XML 拒收、服务端生成 key、请求体 11MB）；M2-T05 验收（6MB、改名的 .exe、30 页、加密 PDF 都被拒，桶里没有对象）；下载带 attachment；企业下载简历前 copyPages 重建（M4-T09）；A26 和已接受风险第 4 行（不扫毒）；GATE-M4 人工复测。
- **缺口**：见 TM-015、TM-016、TM-017。
- **建议去处**：无新增。

#### TM-015 恶意 PDF 拖垮唯一的 app 进程

- **边界**：TB4
- **场景**：上传一个 5MB 以内、页数正常、但内部结构被刻意构造（深层嵌套、超大压缩流）的 PDF。app 在请求里同步调用 pdf-lib 读页数，或者企业下载时 copyPages，事件循环被长时间占住，或者内存冲到 1g 上限被杀。只有一个 app 实例，整站一起不可用。每个账号每小时能传 20 个，开几个号就能持续打。
- **影响**：全站可用性。
- **可能性**：中（pdf-lib 遇到这类文件的耗时和内存表现待核实）
- **等级**：Medium
- **现有控制**：大小和页数上限、拒绝加密 PDF、`limits.uploadsPerHour`、每个企业成员最多 2 个水印任务（ARCHITECTURE §5.5）；容器内存上限（ARCHITECTURE §7）；止血开关 `uploads.enabled`（M7-T14，P1）；E8-18（Worker 沙箱）暂不采用。
- **缺口**：PDF 解析在 app 进程里同步执行，没有超时；E8-18 只在「备选方案」里，没进「已接受风险」表。
- **建议去处**：DECISIONS 已接受风险加一行（§10）；M7-T13 的止血场景加「上传导致 app 卡死 → 关 `uploads.enabled`」。

#### TM-016 运营打开企业上传的恶意认证材料

- **边界**：TB4（连到 TB7）
- **场景**：申请认证的「企业」上传一个针对桌面 PDF 阅读器漏洞的 PDF。运营在审核页点开签名链接，因为带 `Content-Disposition: attachment`，文件下载到运营电脑上、用本地阅读器打开。运营电脑被控制后，后台会话和密码一起丢失（接 TM-026）。
- **影响**：运营后台被接管，进而拿到全部学生数据。
- **可能性**：低（需要定向攻击）
- **等级**：Medium
- **现有控制**：类型白名单和文件头（ARCHITECTURE §5.5）；A26 不扫毒（已接受风险第 4 行）。copyPages 重建（M4-T09）只用于企业下载简历，保护的是企业，不是运营。
- **缺口**：认证材料（以及 M8 的付款回单）给运营看之前没有重建。
- **建议去处**：M3-T03 加一句「运营查看 PDF 材料时，服务端先用和 M4-T09 相同的 copyPages 重建再返回；图片原样返回」（A-22）。

#### TM-017 上传用途和角色不对应，存储被灌满

- **边界**：TB4
- **场景**：
  1. 学生账号 POST `/api/uploads/VERIFICATION` 或 `/api/uploads/LOGO`，企业账号 POST `/api/uploads/RESUME`。规格没写每个用途允许哪些角色；`verifications/` 和 `logos/` 的 key 要用 companyId，学生没有 companyId，实现时容易出错。
  2. 任何登录用户每小时传 20 个 10MB 文件，一天约 4.8GB；上传了但从未被引用的对象没有清理任务（计划 B7 去掉了 PendingUpload）；桶开了版本控制，删了也要 30 天后才真正释放。
  3. 「documentKeys 只能来自本企业自己的上传记录」，但没有上传记录表，实际只能靠 key 前缀判断。
- **影响**：存储费用失控；跨用途、跨企业引用对象。
- **可能性**：中
- **等级**：Medium
- **现有控制**：ARCHITECTURE §5.5（白名单、大小、每小时上限、服务端生成 key）；M2-T05；M3-T02（提交别的企业的对象 key 被拒）。
- **缺口**：用途和角色的对应关系；孤儿对象清理；每个用户的存储总量上限；每小时计数的数据来源（没有上传表，P1 前是内存计数）；PAYMENT_PROOF 和学生证的 key 规则。
- **建议去处**：M2-T05 加验收句「每个 purpose 只允许对应角色，其他角色返回 403；VERIFICATION 的 documentKeys 必须以 `verifications/{本企业 companyId}/` 开头且对象存在」（按 A-21 的答案定）。

#### TM-018 导出包和签名链接久留或外泄

- **边界**：TB4
- **场景**：学生导出数据后，worker 生成的 zip（含解密后的联系方式和全部简历）一直留在 `exports/{userId}/` 下。以后桶凭据泄露，或者删号 purge 没清这个前缀，这份明文就一起出去。签名 GET 链接被转发到群里，5 分钟内别人也能下载。
- **影响**：PII 的明文副本长期存在。
- **可能性**：低到中
- **等级**：Medium
- **现有控制**：PRD §2.3、M7-T03（邮件只放站内链接、本人登录、24 小时内、现场签 300 秒）；ARCHITECTURE §5.5（签名 GET ≤ 300 秒、attachment、私有桶）；M7-T03 的 purge 删除对象全部版本。
- **缺口**：导出对象本身保留多久没写；purge 是否覆盖 `exports/` 前缀没写。
- **建议去处**：M7-T03 加验收句「导出对象 24 小时后删除（含全部版本）；purge 也清该用户的 `exports/` 前缀」（A-24）。

### TB5 邀请、额度、配额滥用

#### TM-019 刷邀请换额度

- **边界**：TB5
- **场景**：学生用一个能收任意地址的自有域名（catch-all）或一次性邮箱，批量注册「被邀请人」，每个号把资料随便填满到完成度 90（不传 PDF 刚好 90）。每天生效 3 个，4 天凑够 12 个，额度变成不限。
- **影响**：额度机制失灵；每个假号占一个注册名额（TB6），挤掉真学生；数据里混进假档案。
- **可能性**：中（收益不大，但方法简单，可能在学生群里传开）
- **等级**：Medium
- **现有控制**：PRD §2.5；M2-T09（邮箱已验证、完成度 90、gmail 规范化防自邀、每天 3 个、只记一个邀请人、作废不计）；Turnstile 和注册限流（M1-T05）；运营作废（service 在 M2-T09，页面在 M6-T08，P1）。
- **缺口**：`referral.requireSchoolVerified=false` 时不需要学校邮箱就能生效；没有一次性邮箱域名名单；试点期运营可能没有作废的页面。
- **建议去处**：按 A-17 决定；如果保持 false，M7-T13 的每周例行检查加「同一邮箱域名下的新注册数」。

#### TM-020 锁定职位的内容从旁路泄出

- **边界**：TB5
- **场景**：
  1. 额度用完的学生、访客，或者聊天软件的链接预览爬虫请求 `/jobs/[id]`。generateMetadata 把描述片段写进 `<meta name="description">` 或 og:description，页面看着是锁的，源码里有正文。M5-T03 只规定 metadata 里不能有隐藏的薪资。
  2. 学生在锁定卡片上直接调用投递接口（规格没说投递前要能打开详情）；投递后「已投递的职位总是允许打开」，再撤回投递，职位就一直开着。
- **影响**：额度机制被绕过；第 2 条还会给企业制造无效投递，并把学生联系方式白给企业（A3）。
- **可能性**：高（第 1 条只需要看网页源码）
- **等级**：Medium（不涉及学生 PII，影响的是增长机制）
- **现有控制**：ARCHITECTURE §5.4（列表白名单、搜索不匹配锁住的描述）；M5-T03（`toJobListItem`、noindex、不输出 JSON-LD、metadata 里没有隐藏薪资、职位侧 pii-leak）；M5-T09；M2-T10、D18（企业账号按访客处理）。
- **缺口**：metadata 规则只管薪资；投递是否要求先能打开详情、撤回后还算不算「已投递」，都没写。
- **建议去处**：M5-T03 加验收句「锁定状态和访客请求 `/jobs/[id]` 时，HTML head（title、description、og:*）里不出现 description、requirements、benefits 的任何片段」；M5-T04 按 A-18 的答案补一句。

#### TM-021 企业邀请投递被用来群发骚扰或诈骗

- **边界**：TB5
- **场景**：认证企业每月有 20 个邀请（`invitations.freeMonthlyQuota`）。附言是自由文本，直接显示给学生，不经审核，企业可以写「加我 WhatsApp，先交押金」。并发发送还可能超出月配额（规格只写了按自然月计算，没写并发控制）。学生端没有举报邀请的入口。
- **影响**：诈骗内容绕过职位审核直达学生；配额略超。
- **可能性**：中
- **等级**：Medium
- **现有控制**：M5-T07（月配额、发送前调 `isStudentVisibleToCompany`、过期任务）；学生可以婉拒；TM-006 的认证。
- **缺口**：附言不审核也不过滤；没有举报入口；配额计数没有并发控制。
- **建议去处**：M5-T07 加一句「附言含 URL、电话、微信号时拒绝（用 redact 的同一套模式检测）；同一企业并发发送不超出月配额」（A-19）。

#### TM-022 用注册提醒和验证码邮件轰炸别人

- **边界**：TB5
- **场景**：攻击者用别人的邮箱（或者试点学校的一批学生邮箱）反复注册，每次系统都发一封「有人尝试用你的邮箱注册」；或者反复给学校邮箱发验证码。学校的邮件服务器把 FindMYJob 的发信域判为垃圾邮件，学校认证邮件从此进垃圾箱或被拒收。
- **影响**：被骚扰的人投诉；发信信誉受损，学校认证和注册验证码送不到，整个试点受影响。
- **可能性**：中
- **等级**：Medium
- **现有控制**：Turnstile、注册 60 秒 3 次（ARCHITECTURE §5.8、M1-T05）；学校验证码每用户每小时、每目标邮箱每天上限（M2-T06）；`email.dailyCap`（M7-T14，P1，E2 前）；SPF / DKIM / DMARC（M7-H01）。
- **缺口**：注册提醒邮件没有「每个目标邮箱每天最多几封」的上限。
- **建议去处**：M1-T05 加一句「同一个已注册邮箱每天最多收 1 封『有人尝试用你的邮箱注册』提醒」。

### TB6 绕过注册上限

#### TM-023 上限只在建号时检查，之后验证邮箱就超出

- **边界**：TB6
- **场景**：上限统计的是「已验证、ACTIVE 的学生」，但 `assertStudentSignupOpen()` 只在 `user.create.before` 里调用（ARCHITECTURE §5.11）。离上限还差 10 人时，学校群里一发通知，几分钟内建了 400 个未验证账号；因为未验证的不算，全部建号成功，之后陆续验证邮箱，已验证学生数变成上限的两倍多。M1-T06 的验收「上限为 3、已有 2 个已验证和 5 个未验证时，第 3 个仍能注册」也说明了这一点。
- **影响**：超出压测过的人数（每次放量按下一阶段人数的 1.2 倍压测）；放量节奏失控。
- **可能性**：高（不需要攻击者，正常推广就会发生）
- **等级**：Medium
- **现有控制**：M1-T06；DECISIONS 已接受风险第 1 行（「并发时可能略超」）；运营看板的上限进度（M6-T01）；运营可随时下调上限。
- **缺口**：已接受风险第 1 行低估了超出幅度：不只是并发略超，48 小时内建的未验证账号都可能在验证后超出。
- **建议去处**：按 A-16 决定。修：M1-T06 加一句「邮箱验证时再检查一次上限，满额时不完成验证、提示名额已满；上限为 3、已有 2 个已验证和 5 个未验证学生时，5 个依次验证后，已验证学生数为 3」。不修：把已接受风险第 1 行的描述改成实际情况，填 TM-023（§10）。

#### TM-024 用假账号占满名额

- **边界**：TB6
- **场景**：有人（竞争者或恶作剧）用 catch-all 域名批量注册并验证学生账号，把 E2 的 200 个名额占满，真学生看到「名额已满」。
- **影响**：试点注册被堵；数据里混进假档案。
- **可能性**：低
- **等级**：Low
- **现有控制**：Turnstile、注册限流（M1-T05）；只统计 ACTIVE 学生，运营停用假号后名额自动空出（M6-T02）；运营看板（M6-T01）。
- **缺口**：没有一次性邮箱或可疑域名的拦截；看板看不到按邮箱域名的注册分布。
- **建议去处**：M7-T13 在 RUNBOOK 写一条处置步骤：按邮箱域名查新注册 → 批量停用。

#### TM-025 借企业注册入口或改角色绕过上限

- **边界**：TB6
- **场景**：Better Auth 的注册走同一个原始接口，role 设成了 `input:false`。为了让企业注册不受上限影响，实现时可能让 `user.create.before` 凭请求里的某个字段或页面来源判断「这是企业注册」并跳过上限，角色在注册后另一步写入。攻击者满额时带上这个字段直接 POST，跳过上限，又不做第二步，账号就停在默认的 STUDENT。
- **影响**：上限被任意绕过。
- **可能性**：中（取决于实现；Better Auth 的 databaseHooks 能否拿到请求上下文，待核实）
- **等级**：Medium
- **现有控制**：M1-T01（role、status 为 `input:false`）；M1-T02（按入口写角色）；M1-T06（直接 POST 注册端点也被挡）；GATE-M4（带 role ADMIN 建出的账号必须是 STUDENT）。
- **缺口**：没写清楚角色在哪一步、凭什么写定；没写「建号后没有任何接口能改角色」。
- **建议去处**：M1-T06 加验收句「满额时，用企业注册入口的请求体直接 POST，建出的账号 role 必须是 EMPLOYER，调用任何学生端 action 返回 403；没有任何接口能把 EMPLOYER 改成 STUDENT」（A-15）。

### TB7 运营后台

#### TM-026 运营账号被盗

- **边界**：TB7
- **场景**：运营的密码被钓鱼或撞库；或者运营电脑中招（TM-016）。`/admin` 直接暴露在公网，E3 之前运营账号没有 2FA。盗号者登录后逐个查看学生联系方式（M6-T02 运营可见全部字段）、改系统参数（关额度、调大查看上限）、给自己控制的企业加点数。
- **影响**：全部学生 PII；平台规则被改。
- **可能性**：中
- **等级**：High
- **现有控制**：每人一个账号、不共用（PRD §1、§4）；登录限流和 Turnstile（ARCHITECTURE §5.8、§5.11）；审计 `auth.login`、`setting.update`、`credits.adjust` 等（ARCHITECTURE §5.7）；应用不能删 AuditLog（M0-T03）；M6-T09（P1，E3 前：2FA、敏感操作要求 10 分钟内的新鲜会话、会话最长 12 小时）；DECISIONS 已接受风险第 2 行。
- **缺口**：E2（200 名真实学生）期间没有 2FA；`/admin` 没有网络层限制（E8-08 不采用，A-28）；种子管理员的密码来自环境变量，到 GATE-M7 才要求修改。
- **建议去处**：DECISIONS 已接受风险第 2 行把「待 B8」改为 TM-026，补偿控制加一句（§11）。

#### TM-027 运营越权或滥用

- **边界**：TB7
- **场景**：某个运营出于私人原因查看某个学生的联系方式，给熟人学生加额度、给熟人企业加点数，作废别人的邀请，或者处理数据请求时把别人的导出包下载下来。
- **影响**：学生 PII 被内部人员滥用。
- **可能性**：低
- **等级**：Medium
- **现有控制**：每人一个账号；ADMIN_GRANT 和 `credits.adjust` 必须填原因；AuditLog 只追加（M0-T03）；审计日志查询（M6-T06）。
- **缺口**：
  - ARCHITECTURE §5.2 规定只有 `contact-access` 能解密，入口只有企业和本人两种；M6-T02 却要求运营能看联系方式，没有对应的函数和规则。
  - ARCHITECTURE §5.7 的必审计动作里没有「运营查看联系方式」「运营加查看额度」「人工学校认证」「停用企业」「设置公司标签」，和 PRD §7「所有后台操作都写审计」不一致。
  - 没有人复核运营的操作。
- **建议去处**：M6-T02 加验收句「运营查看联系方式经 `contact-access` 的专用函数，一次一个学生，每次写审计（建议动作名 `admin.contact.view`），不提供批量导出」（A-23）；ARCHITECTURE §5.7 补齐上面几个动作（规格修订）。

#### TM-028 企业或学生提交的内容在后台和学生端执行脚本

- **边界**：TB7（也影响 TB1 的学生端）
- **场景**：
  1. 企业在官网字段填 `javascript:` 开头的地址，学生在 LinkedIn 字段也这么填；页面渲染成 `<a href>`，运营或企业一点就执行。zod 的 URL 校验是否放行 `javascript:`、所用 React 版本是否拦截这类链接，都待核实。
  2. 职位描述、企业简介、反诈文章如果按 HTML 或 Markdown 渲染（规格没写），可以塞进脚本；运营审核职位时最先看到这些内容。
  3. CSP 在 E3 之前只是 Report-Only（M7-T05），挡不住。
- **影响**：运营会话被劫持（接 TM-026）；学生端被插入钓鱼内容。
- **可能性**：中
- **等级**：Medium
- **现有控制**：React 默认转义；`X-Frame-Options DENY`、nosniff（M7-T05）；CSP 强制模式（M7-T15，P1，E3 前）；会话 cookie httpOnly（ARCHITECTURE §5.8）；非 GET 请求校验 Origin（ARCHITECTURE §5.1）。
- **缺口**：用户可填的 URL 字段（`Company.website`、`StudentContact.linkedinUrl`、`Partner.website`、`Article.videoUrl`）没限制只能是 http / https；富文本格式没定；没有禁止 `dangerouslySetInnerHTML` 的 lint 规则。
- **建议去处**：M0-T07 加一句「ESLint 禁止 `dangerouslySetInnerHTML`」；M2-T04、M3-T01 各加一句「URL 字段只接受 http 和 https，`javascript:alert(1)` 被拒」（A-20）。

### PDPA

#### TM-029 删号后数据没删干净

- **边界**：PDPA
- **场景**：学生申请删号。30 天后 purge 按 M7-T03 删掉 StudentContact、ResumeFile 和对象的全部版本，档案匿名化。但学生的全名、邮箱、手机号还可能留在：`User.name` 和 `User.email`、`StudentProfile.schoolEmail`、`Application.coverNote`、企业写的 `Application.companyNote` 和 `TalentFolderItem.note`、`Invitation.message`、`ApplicationEvent.note`、企业收到的 `Notification.payload`（学生投递或被解锁后里面有全名，M4-T02）、导出包（TM-018），以及已经发出去的邮件。
- **影响**：删除请求没有真正完成，违反 PDPA，学生也不知道。
- **可能性**：高（规格没列清单，实现时很容易只删验收里写到的那几张表）
- **等级**：High
- **现有控制**：PRD §2.3、§7；M7-T03（软删除立即移出人才库、30 天 purge 可重复执行、删除对象全部版本）；备份 30 天过期（A20）；恢复后补跑 purge（M7-T12）；D22（AuditLog 的 IP）。
- **缺口**：purge 的范围没有完整清单；企业侧保留哪些内容没定（A-25）。
- **建议去处**：TASKS M7-T03 加验收句（§11）。

#### TM-030 撤回同意后的效果不清楚

- **边界**：PDPA
- **场景**：学生在隐私中心关闭人才库（等于撤回 TALENT_POOL 同意），以为企业都看不到他了。实际上已经解锁过他的企业、他投递过的企业仍能看到全名和联系方式（只有屏蔽和删号才收回，PRD §2.3）。
- **影响**：学生的预期和实际不符；撤回同意后已授权的使用能否继续，要律师确认。
- **可能性**：高
- **等级**：Medium
- **现有控制**：PRD §2.3（HIDDEN 立即从人才库消失；屏蔽会收回已解锁的联系方式）；Consent 只追加；M2-T07；GATE-M4（关闭人才库后立即从搜索结果消失）。
- **缺口**：页面上没说清楚「关闭人才库」和「屏蔽」的区别；D10 的律师问题里没有「撤回同意后，已获授权的企业能否继续使用联系方式」。
- **建议去处**：按 A-12 决定；D10 加一个律师问题；M2-T07 加一句页面说明。

#### TM-031 学生证人工认证收集了证件号和照片

- **边界**：PDPA
- **场景**：没有学校邮箱的学生按 PRD §2.1 上传学生证，由运营人工审核（M6-T02）。学生证上通常有照片和学号，国际生的有时还有护照号。这和 PRD §7「不收集身份证号 / 护照号、照片」冲突。规格也没有对应的上传用途、key 规则和保留期，材料可能永久留在桶里。
- **影响**：收集了 PRD 明确说不收集的数据；一旦泄露后果更重。
- **可能性**：高（只要这个功能上线）
- **等级**：Medium
- **现有控制**：无专门控制。
- **缺口**：见场景。
- **建议去处**：按 A-26 决定：试点期不做学生证认证；或者要求打码后上传、审核完立刻删除，并补上传用途、key 规则和保留期。

#### TM-032 未成年用户

- **边界**：PDPA
- **场景**：预科（`DegreeLevel.FOUNDATION`）学生可能未满 18 岁。注册、加入人才库、被企业解锁联系方式，都以本人同意为依据。
- **影响**：同意可能无效；企业联系未成年人需要额外保护。
- **可能性**：中
- **等级**：Medium
- **现有控制**：无。
- **缺口**：没有年龄确认；D10 的律师问题里没有这一项。
- **建议去处**：按 A-27 决定；把「未成年人的同意和人才库可见性」加进 D10 律师问题。

#### TM-033 跨境传输没有如实披露

- **边界**：PDPA
- **场景**：学生数据或其衍生数据流到马来西亚以外：Sentry（EU，D14）；Resend 处理的邮件正文（企业收到的通知里有学生的脱敏卡片，投递后有全名）；Turnstile 收集访问者 IP。这几家的所在区域在 SUBPROCESSORS 里多数写着「待核实」。隐私政策没写或写得和实际不一致，就违反告知要求。
- **影响**：合规风险。
- **可能性**：中
- **等级**：Medium
- **现有控制**：SUBPROCESSORS 清单；D10 律师问题 ①；M7-T02（隐私政策披露子处理者和跨境传输）；Sentry 脱敏（M7-T04）；DECISIONS 已接受风险第 3 行；GATE-M7 律师书面确认。
- **缺口**：Resend、Turnstile 的区域待核实；SUBPROCESSORS 的 Resend 一行没写「企业通知里含学生姓名和档案摘要」。
- **建议去处**：SUBPROCESSORS 的 Resend 一行补数据类别；GATE-M7 前核实区域；已接受风险第 3 行填 TM-033（§10）。

#### TM-034 个人数据没有保留期

- **边界**：PDPA
- **场景**：ProfileView（只展示 90 天，但一直保存）、`AuditLog.ip`、Session 的 IP 和 UA、Consent 的 IP 和 UA、Notification、已关闭的职位和投递记录，都没有保留期；数据越积越多，泄露时影响面越大。
- **影响**：可能不符合数据最少保留的要求（具体以律师意见为准）。
- **可能性**：高（默认就是永久保存）
- **等级**：Low（试点规模小，可以在 E4 前补）
- **现有控制**：备份 30 天（A20）；对象旧版本 30 天（ARCHITECTURE §5.5）；D22。
- **缺口**：每张表的保留期。
- **建议去处**：D10 加律师问题「各类记录保留多久」；E4 前加清理任务。
